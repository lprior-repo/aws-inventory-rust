Continue the Rust AWS CMDB project in this directory.

What we are building: a CMDB of every AWS resource, read through the services' own endpoint APIs by our own wire engine, kept current by repeated sweeps, stored in SQL and a relationship graph, and shown as a Makepad DAG. Sweep and reconcile speed is the selling point. It runs on one laptop first. Read docs/VISION.md before anything else: its section 2 holds the owner's decisions and it wins over every other document. Then read docs/ROADMAP.md, which is the build plan. Take the first unfinished work package whose needs are done.

The owner's hard rules:
- No Cloud Control. The Cloud Control collectors in the tree are the baseline being replaced; do no new work on them and delete them when the roadmap says so.
- Collection goes through our own wire engine, driven by the pinned official AWS API models. Do not add typed AWS SDK service crates. AWS crates are for credentials and signing only.
- No JSON on the data path. An AWS response is parsed once into a binary record; JSON exists only in an explicit export.
- Code is a liability. A service is described by data (models plus a reviewed overlay), never by Rust. Delete what you replace in the same change.
- All product code is Rust. The Python scripts under scripts/ and catalog/upstream/ are frozen legacy tooling: do not extend, port or plan around them.
- Performance claims come only from measurements, and "fastest" only from head-to-head runs.

Engineering rules:
- Workspace lints apply: no unsafe, unwrap, expect, panic, todo, unchecked indexing or lossy casts. Files at or under 300 lines, functions at or under 25.
- Every queue, batch, retry, response and traversal is bounded. No detached tasks. One retry owner.
- State that matters lives in the store: work queue, pagination position, learned rates, scope outcomes. A killed process resumes.
- Collection is read-only. Never create, enable or modify anything in AWS. Never call an operation the catalog has not classified. Never read content, secrets or key material. Use real AWS only in an account the owner has authorized.
- Prove behavior against the pinned emulator with real signed requests before calling it working. The emulator proves serialization, decoding, pagination, retry, storage and delivery; it does not prove real provider semantics, IAM, quotas or eventual consistency. Report emulator and real-account evidence separately.
- Implemented, emulator-verified and live-verified are separate facts. Deleted, unobserved, inaccessible and unsupported are separate states. Partial is a stored, reported result.
- Take numbers from the tree and the catalog, not from documents.
- Keep Cargo targets on disk-backed storage and run one heavy Cargo build at a time. A server and its clients must share one owned process lifetime.
