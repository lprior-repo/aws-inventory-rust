# Inventory export and FalkorDB delivery

> Status: Kept and extended. Explicit JSON export and FalkorDB as a rebuildable
> projection of SQL are kept (V03, V14); delivery at the end of a `scan` and
> whole-snapshot projection are baseline, replaced by the pending-projection
> queue and delta projection in ROADMAP M6.1 and by the removal of the old
> `scan` path in M9.5. See [VISION](VISION.md) and [ROADMAP](ROADMAP.md).

Version 0.5 connects collection, portable inventory files and graph projection.
SQLite remains the durable inventory. A delivery failure does not discard a
scan or cause its AWS API calls to run again.

## Collect and deliver in one invocation

```bash
export FALKORDB_URL='redis://127.0.0.1:6379'
cargo build --locked --features aws --bin aws-inventory

target/debug/aws-inventory scan \
  --region us-east-1,us-west-2 \
  --service all --cloud-control --discover-sources \
  --db inventory.sqlite --output-dir outputs \
  --provenance all-observations --falkor --allow-partial
```

The scanner uses the selected profiles/accounts and regions. `all` selects the
implemented native groups; `--cloud-control` adds the reviewed provider catalog.
`--discover-sources` looks for existing Config and Resource Explorer sources.
It does not create those services, their indexes or their recording configuration.

After collection finalizes, each snapshot is exported sequentially. JSONL is
the default; `--export-format json` creates a JSON document instead. Both formats
stream records from SQLx. They contain resources, edges, collection scopes,
failures, the scan's actual status and a final count summary. They do not use the
interactive SQL command's 10,000-row result limit.

`--falkor` also exports an idempotent Cypher plan and applies it to the configured
FalkorDB destination. The URL is read from `FALKORDB_URL`; use
`--falkor-url-env NAME` to choose a different variable. Only the variable name
is persisted in durable job intent. The URL value is not written to receipts.

`--allow-partial` deliberately includes finalized partial or cancelled snapshots
with their real status. Without it, such snapshots remain in SQLite and delivery
records a `skipped` outcome. A running snapshot is never exported. An interrupt
during the current scan stops new deliveries even when `--allow-partial` was set.

## Export or retry an existing snapshot

```bash
target/debug/aws-inventory export --db inventory.sqlite --scan-id SCAN_ID \
  --output inventory.json --format json --provenance all-observations \
  --allow-partial

target/debug/aws-inventory deliver --db inventory.sqlite --scan-id SCAN_ID \
  --output-dir outputs --falkor --allow-partial
```

`export` writes a portable inventory artifact. `graph-export` writes Cypher
batches encoded as JSONL; these are different, explicitly identified formats.
The portable artifact is not the `CollectionEvent` input format of `ingest`.
See [EXPORT.md](EXPORT.md) for record schemas, ordering, bounds and provenance.

`deliver` performs no AWS collection and does not load AWS credentials. Each
attempt publishes into a new `outputs/SCAN_ID/ATTEMPT_ID` directory, preserving
prior artifacts. That directory contains `inventory.jsonl` or `inventory.json`,
`graph.jsonl` when requested, and `delivery.json` with the outcome. A completed
inventory file may remain available even if the later graph push fails. The
receipt identifies the attempt directory and explains recovery.

Graph acknowledgements are held in `outputs/projection.sqlite`. Retrying
`deliver` with that output directory regenerates the immutable plan and skips
already acknowledged batches. The checkpoint binds destination, graph, scan,
sequence and content digest. An existing acknowledgement with changed batch
content fails explicitly. Use the original plan with `graph-push` when continuing
a plan generated by an older version whose graph serialization has changed.

```bash
target/debug/aws-inventory graph-push --input outputs/SCAN_ID/ATTEMPT_ID/graph.jsonl \
  --checkpoint outputs/projection.sqlite --attempts 5
```

After an external graph reset, use a fresh checkpoint database. The tool cannot
infer that the server lost previously acknowledged data. Concurrent processes
pushing the same graph/snapshot are outside the current delivery contract.

## Status and failure contract

Scan results retain `collection_status` and add one delivery receipt per scan.
An otherwise complete collection becomes overall `partial` when requested
delivery fails or is skipped. A partial collection stays partial even if its
export succeeds. Cancellation stays visible. The CLI returns exit 2 for partial
or cancelled output, exit 1 for command/configuration errors, and exit 0 for a
complete requested operation.

The scan does not become complete merely because files were written or the
graph accepted them. Scope failures and missing-provider evidence remain part
of the inventory and graph snapshot marker.

`--delivery-attempts` bounds attempts per graph batch (default 5, maximum 10).
`--delivery-timeout-seconds` bounds each scan's export plus graph delivery
(default 900, allowed 1 through 86,400). Retry backoff counts against that budget.
A deadline requests cancellation and allows up to 30 seconds for cleanup. A
timeout with incomplete cleanup is reported explicitly; it is not a successful
delivery. Cooperative cancellation is passed into file exporters and graph
delivery so temporary files and SQLx acknowledgements have an owned lifecycle.

Graph writes use idempotent MERGE operations. A transport failure after a remote
write but before its response can be retried. The local ACK is committed only
after server success. Authentication, invalid query and other permanent failures
are not converted to infinite retries. See the graph retry documentation for
the exact classification and independently exercised cases.

## Durable jobs

```bash
target/debug/aws-inventory job submit --queue jobs.sqlite \
  --db inventory.sqlite --region us-east-1 --service all --cloud-control \
  --output-dir outputs --falkor --allow-partial
target/debug/aws-inventory job run --queue jobs.sqlite --limit 1
```

Submission validates the intent without reading destination credentials or
calling AWS. The worker performs delivery under its existing lease/cancellation
supervisor. Old version 0.4 job payloads default to collection only. A worker
retry still represents a new scan attempt; to finish delivery for an already
finalized scan, use `deliver` and its scan ID.

## Storage upgrade

SQLite schema 5 adds the new source-specific Cloud Control views. The historical
200-view migration is retained. The added views are installed transactionally,
without rebuilding observations, altering finished scans or replacing caller
views. A name conflict fails and rolls back both the added views and schema
version. The migration tests preserve existing data and exercise that rollback.

## Release packaging

The portable source/evidence ZIP is built by the Rust catalog tool; no Python
interpreter is involved:

```bash
cargo run -q -p catalog-tool -- package --destination /path/to/aws-inventory-rs.zip
```

`--root` overrides the payload root (default: the workspace). The command scans
the tree, excludes Cargo targets and caches, VCS data, credential material and
non-published databases exactly as the former Python packager did, writes
`MANIFEST.sha256` beside the sources and embeds it in the archive. Entry order is
the sorted slash-separated relative path, and every entry carries a fixed
1980-01-01 ZIP timestamp and deterministic deflate settings, so repeated runs
over an unchanged tree produce byte-identical archives (the retired Python tool
embedded the current time instead). The archive is written through an exclusively
created temporary file in the destination directory, re-read to verify the entry
count, every payload hash and the manifest, then atomically renamed. Failed
publication removes the temporary file and preserves an existing destination.
Pre-existing sibling files are never reused. Destination symlinks are replaced
themselves by rename, never followed.

`MANIFEST.sha256` is also published by exclusive temporary-file replacement,
at the same point after payload collection and with the same manifest bytes.
Manifest symlinks and hard links therefore cannot truncate their targets.
On Unix, all shared-writer outputs request mode `0666` during exclusive creation;
the kernel applies the current umask, just as for `File::create`.

Choose a destination outside the packaged root: destinations whose canonical
parent is inside the canonical root are rejected as invalid input before any
writes, with both paths in the error. This also applies through directory
symlinks and prevents output self-inclusion or replacement of selected sources.
An existing external destination (for example yesterday's ZIP) is still replaced.
The command prints a JSON receipt with `path`, `files`, `bytes` and `sha256` for
the finished archive. `inventory-harness` uses this same implementation; SDK
generated files use its shared exclusive atomic-file writer.

The destination directory must not be writable by untrusted users: pathname
validation is not atomic with publication, and hostile concurrent directory
replacement is outside this developer tool's threat model.

Packaging prunes excluded directories before descent and rejects inputs beyond
64 directory levels, 100,000 visited entries, 64 MiB per included file, or 1 GiB
of total included payload bytes. Byte budgets are checked from metadata before
reading and reserving file buffers; a growing file cannot enlarge its reserved
snapshot. Limit errors are typed invalid-input failures naming the path and
maximum. These ceilings are provisional: no real release-package size receipt
was found in the documentation. The completed archive digest is streamed through
a fixed 8 KiB buffer rather than loading the archive into memory again.

## Verification boundaries

The implementation includes offline artifact/status/cancellation tests, a
schema-upgrade regression and an actual CLI integration that collects from the
official AWS Emulator, exports JSONL, pushes to a local FalkorDB instance and
resumes the same scan. Execution receipts in the verification report state which
of those tests have run for a particular source snapshot. Test code existing in
the repository is not itself evidence that its most recent revision passed.
